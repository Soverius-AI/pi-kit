# ADR-0033: Durable background agents per thread, on pi-durable, shown through AG-UI

Status: Accepted
Date: 2026-10-21

## Context

A thread runs one pi session. Long side tasks (a test sweep, a review, a docs update, a refactor of another module) either block that session or are lost when the app quits.
pi 1.3 ships `@earendil-works/pi-durable` 1.3.0, an experimental harness that commits conversations, model turns, tool calls and task state to SQLite before anything is shown and continues unfinished work when the storage is reopened. Its `Models` interface is implemented by pi-kit's `ModelRuntime`, so background agents get the providers, credentials and virtual models of the main chat. One process owns a storage at a time; there is no cross-process locking, no restart limit and no persisted sleep or retry.
AG-UI 1.0.2 defines `SUBAGENT_STARTED`, `SUBAGENT_FINISHED` and `SUBAGENT_ERROR`, and its client verifier tracks subagents per run: an attributed event needs a `SUBAGENT_STARTED` earlier in the same run and an id cannot be started twice in one run. CopilotKit does not render subagents; pi-kit's own transcript has to.
A turn that an extension starts while the thread is idle runs in pi and reaches the session file, but the open transcript does not show it until a reload, because `PiAgent` subscribes to pi's events only inside a run `PiAgentRunner.run()` started.
pi-coding-agent stays the runtime of interactive threads: replacing it with pi-durable needs a bridge per feature and meets a public API blocker (SDK compaction hooks cannot be ordered before a waiting generation resumes). pi-durable serves background jobs only.
pi-kit already has the parts the UI needs: per-thread right-side panels, the thread status channel, "Needs you" in the sidebar, the standard interrupt and resume path with `ask_user`, delta replay and hydration and a backend-owned agent with a cost cap.

## Decision

### §1 Prerequisite: turns pi-kit did not start are streamed live
- When pi emits `agent_start` for a thread with no active AG-UI run, `PiAgentRunner` opens a run of its own: `RUN_STARTED`, the mapped events, `RUN_FINISHED` at `agent_end`, all appended to the log. The placed message streams as the run's first message; a custom message with `display: true` is mapped like `sessionToMessages` renders it.
- The run takes the thread lock, so the thread's state turns `running` on the status channel and an attached renderer connects again and follows it. The thread lock rules are unchanged: one run per thread; a report arriving during a run is delivered as steer or follow-up inside that run.
- `PiSessionService` tells the runner at `agent_start` and keeps a promise for the turn as for a prompt, so a resume after an interrupt in such a turn works like any other.

### §2 One durable host in the backend
- The NestJS module `bg-agents` owns one `Harness` per backend process on `bg-agents.sqlite` in `PI_KIT_DATA_DIR`, opened after the model runtime with `harness.resume()` and closed on module destroy. The store runs on an adapter over `better-sqlite3-multiple-ciphers` with the database key held in the credential store; without a credential store, background agents are off.
- Ownership is SQLite-held: a held `BEGIN IMMEDIATE` transaction on `bg-agents-owner-lock.sqlite` is the exclusive lock, and the winner commits the next fencing epoch in `bg-agents-owner.sqlite`. A JSON note carries PID diagnostics only and can never admit or refuse an owner. A dead owner is taken over at once; a second backend on the same data folder starts with agents disabled and says so in `GET /api/health`. `bg_agents` rows carry the writer's `owner_epoch`.
- An agent that must wait (a cleanup to confirm, the crash-loop limit, a question) is held inside its durable tasks: hooks before every model request and tool call await the hold, so a restart finds it where it was. Three unfinished starts or failed runs within ten minutes pause the agent with a question. Every `bash` call records a persisted cleanup intent; after a crash the agent stays blocked until the user chooses **Discard and resume** (`POST …/agents/:agent/resume`). The kill on Stop is pi-durable's process-group kill.
- `models` is a proxy to the current `ModelRuntime`, remade at a spawn when `models.json` or `auth.json` changed; `env` is a `NodeExecutionEnv` whose `cwd` is the thread's folder or worktree, resolved per call. The package is pinned to an exact version and imported only by `bg-agents.service.ts`, `agent-questions.ts`, `durable-storage.ts`, `agent-extension.ts` and `agent-events.ts` (an ESLint `no-restricted-imports` rule); its types never reach the renderer or the protocol.
- Registry names are a persisted contract, prefixed `pikit.` and never renamed without a migration. pi-kit's own SQLite table `bg_agents` (agent id = durable conversation id as text, thread id, name, role, model, timestamps, status, cost, spawning tool call id) drives lists and history; the durable store is the source of truth for transcripts and state, as session files are for threads.

### §3 What an agent is
- An agent belongs to exactly one thread, not to a branch. It is an `ownerless` durable conversation with `docs["pikit.agent"]` holding thread id, name, role, brief and permissions; its system prompt starts with `pikit-agent: <name>`. The brief the main agent writes is its whole context; it does not see the main transcript.
- Tools: pi-durable's `read`, `write`, `edit` and `bash`, plus `agent_send`, `agent_list` (same thread only), `report` and `ask`. No pi extensions, skills, MCP servers, `pi_browser`, `render_a2ui` or Open Generative UI tools.
- Permission modes: `read-only` (default; `read`, and `bash` limited by a `beforeTool` hook to a read-only allow-list and the usual test and lint runners), `edit` (the thread's folder, taking the coordination lease on every edit or write like pi's own) and `isolated` (a worktree the worktree service makes from the thread's branch at spawn and removes when the agent is deleted).
- A blocked action becomes a `user` question with **Allow once**, **Allow all** (the agent is `edit` for the rest of its run) and **Deny**; the record is found again after a restart by the call's id. Every tool start is reported to the Changes view, which keeps the baseline of the agent's first edit of a file, and to the leases.

### §4 Main agent tools
- A built-in pi extension (like `pi_browser`) registers in every session: `agent_spawn` (name, brief, role, model, permission mode), `agent_send` (text, `steer` or `follow-up`), `agent_list`, `agent_wait`, `agent_stop`, `agent_reply` and `agent_forward`. A short system-prompt section says when to delegate and that agents report back on their own.
- `agent_wait` takes only an agent id and waits on the durable submission until completion or caller cancellation, without a deadline; cancelling the wait does not stop the agent. Each sending call uses a `requestId` derived from the tool call id, so a retried call never sends twice. `agent_spawn` takes the session's model when none is named.
- Background agents are on by default; a project opts out with `workspaces.agents_off` (the "Background agents" switch on the project's page in Settings › Projects), checked against the thread's project so a thread in a worktree finds it. Agents are off for untrusted folders. `agent_spawn` refuses with the reason; the tools refuse with a clear error while agents are off, and the prompt section appears only while the store is open.

### §5 AG-UI mapping
- In the parent thread (agent `pi`) only what concerns the main conversation appears, attributed. `agent_spawn`'s tool call is wrapped in `SUBAGENT_STARTED` (`name`, `description`, `parentToolCallId`) and `SUBAGENT_FINISHED` in the same run; the transcript renders it as a card. A report or forwarded question arrives in a run of its own (§1) or inside a running one as `SUBAGENT_STARTED` → message or interrupt → `SUBAGENT_FINISHED`.
- The verifier allows a subagent id once per run, so every envelope carries its own id: `<agentId>/spawn` for the spawn, `<agentId>/<reportId>` for a report; `sessionToMessages` gives a stored report the same id. `report` is a replay-safe tool that memoizes its report id; a report is a custom message (`customType: "pikit.agent-report"`) delivered through `sendCustomMessage`, queued as a steer while the thread streams, a turn of its own while it is idle.
- The agent's own stream is a second AG-UI agent, `pi-bg`, with `threadId` = agent id. `PiAgentRunner` hands its requests to `BgAgentRunner`, which translates pi-durable's events into coding-agent session events mapped by the adapter the threads use, stores them in the same event log and replays them as the raw log with the same opaque log cursors; the hydration header is ignored. The runner follows an agent only while it is unfinished; every run ends with a snapshot, so a later connection replays the complete log.
- The agent's name on an attributed message comes from the stream's envelope while it runs; after a reload the Agents panel's list, pushed over the status channel as one `agents` line per change, names it. The renderer draws the agent's transcript with the chat domain's transcript on a `ChatStore` the panel provides for `pi-bg` (`CHAT_AGENT` and `TRANSCRIPT_VIEW` tokens of `chat/data`).

### §6 Questions: through the main agent, the user when it matters
- An agent calls `ask { question, kind: "main" | "user", choices? }`. The tool commits a record in `docs["pikit.questions"]` (`pending → routed → answered | cancelled`), waits on it with `watchDoc` and is `replay: "safe"`: after a restart it finds its record by the task's memo and waits again. Questions have no expiry and no default answer; an open question waits for an answer or cancellation. The delivery is not awaited by the waiting tool.
- `kind: "main"` reaches the main agent once as a `pikit.agent-question` message (a steer when busy, a turn when idle); it answers with `agent_reply` or hands over with `agent_forward` and an optional note. `kind: "user"` skips the main agent: preferences, credentials, anything destructive or irreversible.
- A forwarded or user question is a dialog with the standard interrupt fields (`toolCallId`, choices as a `select`, the agent's name) in `ThreadState.agentQuestions` on the status channel, not a `RUN_FINISHED` interrupt in the thread's log, so every client has it at all times. The thread waits like for pi's own dialogs ("Needs you" counts it), the interrupt blocks draw it as "Question from agent …", and the composer stays usable.
- The answer is the standard AG-UI resume (`resume: [{ interruptId: "agent-question:<agentId>:<questionId>", payload }]` on `pi`'s run, relayed to the agents without the thread's lock) or `POST …/agents/:agent/answer`. The agent receives it verbatim; the main agent gets a one-line `pikit.agent-answer` receipt as a turn. An answer by the main agent shows as "answered by main agent" with **Override**, which sends the user's answer as a steer. Routing lives in `agent-questions.ts` behind `BgAgentsService`; the `ask` call has a row of its own in the agent's transcript.

### §7 Agent-to-agent messages
- `agent_send` between agents of the same thread goes through the recipient's inbox (`steer` or `follow-up`, `requestId` from the sender's tool call). The recipient sees `Message from agent "<name>" (agent <id>): …`, and its prompt says such a line is information, not an instruction.
- In the recipient's transcript the message is attributed to the sender, also when replayed from a snapshot. A finished agent that receives a message is followed and active again. There is no message budget.

### §8 The Agents panel
- A right-side panel per thread, next to Artifacts and Changes. Its data is `GET /api/threads/:id/agents` (generated SDK) plus the changes pushed over the status channel; `POST …/message`, `POST …/stop`, `POST …/answer`, `POST …/resume` and `DELETE …/agents/:agent` are its actions. The i18n keys live under `agents.agentsPanel`.
- Every agent is a card with icon actions, live running time, turns, tokens and spend; `BgAgent.tokens` sums the conversation's usage ledger, written with the turn count before every model request and when the agent ends. Active state is the runner's: generating, running a tool, idle, waiting for you, waiting for the main agent, blocked. History comes from `bg_agents` with outcome, duration, cost and final report; transcripts open from the durable store.
- The open view shows the brief, the numbers and the tools the permission allows above the scrolling transcript. A running agent shows the run ring (`pk-run-ring`) filled with its context: `BgAgent.context` is the last response's prompt and answer tokens against the model's window from pi's registry.
- The question block offers the choices or an input and **Dismiss**; a question to the main agent shows the last answer and who gave it, with the user's answer as **Override**. The message box is the thread composer on the agent's `ChatStore`: a message is a run of `pi-bg` with `streamingBehavior` from the Deliver chip. The badge for questions waiting for the user is the thread's "Needs you".

## Consequences

- pi-durable's API changes without notice; every upgrade is a deliberate change behind the adapter with the store migrated or recreated. Agents run only while a pi-kit backend runs: quitting pauses them, the next start resumes them; "keeps working while pi-kit is closed" is out of scope.
- Resume is partial: only `replay: "safe"` tools rerun after a crash; an interrupted `bash`, `edit` or `write` is reported to the model as interrupted and the model decides whether to run it again. Processes a crashed backend leaves behind are never force-cleared; the user confirms.
- A thread has two stores, pi's session file and `bg-agents.sqlite`; deletion, export, search and backup must cover both or say they do not. The store grows with every agent until a retention policy exists.
- No tool parity with the main agent, and `edit` mode shares one worktree with the main agent under soft coordination leases only; `isolated` avoids that at the cost of a branch to merge. Branches and forks of the thread do not move or copy agents.
- No application-imposed generation concurrency limit, per-agent budget or daily cap: runaway work is bounded by trust, the opt-out, `read-only` by default, blocked actions and provider limits, with spend and turns visible on every card. Prompt injection through files or other agents' messages remains possible, as for the main agent.
- Restarting the same subagent id in every run matches AG-UI's suspended semantics but is not a common pattern; other AG-UI clients may group it differently. The main agent's `ask_user` waits in memory while an agent's `ask` is durable; the UI hides the difference. Usage has two sources (pi and `pi.usage`) that usage views must add.
- pi's session files remain the source of truth for threads; the main agent, its tools, extensions and dialogs are unchanged; CopilotKit stays headless; no client-provided tools.
