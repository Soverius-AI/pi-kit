# ADR-0037: Promise-only SQLite off the JavaScript event loop

Status: Accepted
Date: 2026-11-17

## Context

The backend serves health checks, SSE, tools and inference in one Node process. A Promise-returning repository does not prevent a synchronous SQLite driver from blocking that process: preparing, stepping, checkpointing and committing still run on the JavaScript thread. Inference can produce enough replay and metadata writes to make unrelated requests wait. Moving only HTTP handlers or wrapping synchronous calls in `async` does not solve this.

The previous database driver also supported encrypted profiles. Changing that boundary must not mistake an encrypted file or an unavailable key for corruption, silently replace a profile, or claim equivalent at-rest protection from a driver that cannot open those files.

## Decision

- Use AppThreat's `@appthreat/sqlite3` asynchronous native driver through the backend's `AsyncSqlite` façade. Runtime repositories await `prepare(sql).get/all/run`, `exec`, `pragma` and `close`. There is no synchronous-driver fallback or blocking wait bridge.
- Remove the legacy synchronous drivers, database-encryption settings, recovery helpers and recovery-key API/UI, including the `PI_KIT_DB_KEY` override. No legacy driver or alias, in-app migration, decryption, key-file import or key-export tooling is shipped. No database keys are read. Drizzle remains for schema declarations and row types only; runtime queries use the asynchronous driver. Existing stored legacy database keys are not deleted.
- One queue owns each connection. An awaited transaction callback retains exclusive ownership through commit or rollback; nested transactions use savepoints. Read/check/write guards and write/read return snapshots belong inside the same transaction. Sequential insert/delete loops await each operation, rather than launching unobserved asynchronous `forEach` callbacks.
- `DatabaseService.create()` and the Nest provider factory await opening, migrations and instance identity hydration before consumers are constructed. The immutable local `instanceId` remains a synchronous cached property; repository constructors do not query SQLite. Shutdown drains accepted work and awaits close after domain cleanup.
- Native statement caching stays disabled. Even with drained `get()`/`all()`, a cached row-producing `run(... RETURNING)` can leave a native VM active and make commit fail. Measured hot-query speedups do not justify weakening cursor/transaction correctness.
- Bulk event deletion uses bounded, parameterized sets inside one transaction rather than one async native dispatch per sequence. Chunking retains thread scoping and all-or-nothing rollback.
- WAL and existing SQL migrations remain the storage contract. Replay event IDs are allocated by SQLite and can have gaps. Security-sensitive repository writes fence `synchronous = FULL` around the complete transaction and restore the previous setting afterwards; unrelated statements cannot enter that scope.
- Fresh app and background-agent databases are private **plaintext** files. Provider credential storage and sealed instance signing keys are separate capabilities; enabling a credential store does not enable database encryption in this backend. Use OS full-disk encryption for database at-rest protection.
- Before opening either profile database, reject an encrypted or unrecognized existing header and pending encryption-transition artifacts. Retain the originals and report an actionable error. Do not automatically reset a profile, decrypt in place, generate replacement keys or downgrade an encrypted profile to plaintext.
- For unsupported encrypted/unrecognized or damaged databases, show one native confirmation: **Quit** (default and Escape) or **Delete and recreate database**. The latter explicitly authorizes a fresh start, not data-preserving conversion. Before replacement, automatically back up the original database files to a private, timestamped, uniquely named directory. There is no second confirmation or success dialog; the dialog ends with the backend's error as **Details**. Database-version errors for incompatible schemas are Quit-only and ask for the matching pi-kit version: they usually mean an older build opened a newer profile, which the newer build still opens. Compatible plaintext upgrades run normal schema migrations without a prompt.
- Only the service host can perform the backup/reset operation, only for the attached desktop app, while the backend is fully stopped and not starting. Archive both app and background-agent databases, their WAL/SHM/journal sidecars, legacy `.plaintext` / `.encrypted` / `.encrypting` / `.decrypting` artifacts and sealed instance identity. Preserve provider credentials, legacy stored keys, UI and other settings, and pi session files. Database metadata, instance identity and pairing reset; pi sessions are retained rather than converted from the old databases.
- Write a root `database-reset-pending.json` marker before moving profile files. Any interrupted backup/reset fails closed before databases open. When the backup's `backup.json` records it as completed, the host clears the marker on the next start. Otherwise the desktop offers **Restore original files** (default) or **Quit**; restore moves back every file without a different copy in the profile, names any conflict and keeps the marker until all are resolved. Repeating reset must not bypass the marker or silently proceed from a partially archived profile. Failures never automatically reset the profile.
- Actual data-preserving conversion of encrypted contents requires a compatible previous encryption-capable build and the original key offline, followed by validation before using plaintext files. This build supplies no conversion or key-export tooling and never decrypts an encrypted profile.

## Consequences

- Database work no longer blocks the JavaScript event loop merely because SQLite is stepping a statement. Large result mapping, JSON serialization and filesystem work can still require their own bounds.
- Repository methods and their callers are asynchronous, including tests and shutdown hooks. Tests use `await DatabaseService.create(...)`, await every operation and close before removing temporary folders.
- Concurrency is now observable between awaited operations. Atomic guards, stable returned snapshots, per-thread event ordering and durable-before-publish boundaries need regression tests, not just type-checking.
- Existing supported plaintext profiles retain their metadata and normal schema migrations. Unsupported encrypted profiles fail closed unless the owner explicitly chooses delete/recreate with an automatic backup, or performs compatible offline conversion using a previous build and the original key. Fresh start retains original files for later recovery but resets database metadata and pairing; it does not migrate encrypted contents.
- This decision supersedes the runtime-driver and database-encryption portions of [ADR-0003](0003-pi-sessions-are-the-source-of-truth.md), [ADR-0010](0010-durable-threads.md), [ADR-0019](0019-secrets-at-rest.md), [ADR-0022](0022-latest-dependencies.md) and [ADR-0033](0033-durable-background-agents.md). Their source-of-truth, replay, credential and ownership decisions remain in force.
